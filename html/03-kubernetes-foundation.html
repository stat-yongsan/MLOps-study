핵심 6

03장의 뼈대입니다. 포장(Docker), 관리(Kubernetes), 배치(Deployment), 연결(Service), 자동 배포(CI/CD), 관측(Prometheus·Grafana) 순서예요.

Docker이미지 · 컨테이너포장

앱과 실행에 필요한 모든 것을 이미지로 포장하고, 어디서든 같은 방식으로 실행하게 하는 도구.

비유
밀키트. Dockerfile은 조립 설명서, 이미지는 포장이 끝난 밀키트, 컨테이너는 뜯어서 조리 중인 한 그릇, 레지스트리는 물류 창고입니다.
왜 필요해
"내 PC에서는 되는데요" 문제를 줄입니다. 파이썬 버전과 패키지까지 상자째 보내기 때문이에요.
엑셀로 치면
매크로 파일을 보냈더니 받는 사람 PC에 애드인이 없어 안 돌아가는 일. 엑셀, 애드인, 설정까지 한 상자에 담아 보내는 셈입니다.
이번 실습에서
docker build -t income-api:study-v1 .로 포장하고 docker run -p 127.0.0.1:18000:8000으로 실행합니다. PC의 18000번으로 들어가면 컨테이너 안 8000번 앱에 닿아요.
주의
빌드 성공은 포장이 끝났다는 뜻이지 API가 잘 뜬다는 뜻이 아닙니다. 실제로 띄워 요청을 보내 봐야 해요. CPU 종류나 GPU 드라이버 같은 환경 차이도 다 사라지지는 않습니다.
Kubernetesk8s · 쿠버네티스관리 본부

컨테이너를 어느 컴퓨터에 몇 개 띄울지 정하고, 선언한 상태를 계속 유지하는 관리 체계.

비유
공장 관리 본부. 접수 창구(API server)가 주문을 받아 장부(etcd)에 적고, 배치 담당(Scheduler)이 작업장을 고르고, 현장 반장(kubelet)이 기계(런타임)로 작업자를 세웁니다. 조정 담당(Controller)은 온도조절기처럼 목표와 현재를 계속 비교해요.
왜 필요해
docker run을 손으로 반복하면 서버가 늘수록 관리가 무너집니다. "2개 유지"라고 적어 두면 하나가 죽어도 알아서 채워요.
엑셀로 치면
목표값 찾기. 목표를 정해 두면 맞을 때까지 값을 조정하죠. 쿠버네티스는 이 조정을 멈추지 않고 계속합니다.
이번 실습에서
Minikube 클러스터의 ml-book-study 구역에 앱을 2개 띄웁니다.
주의
쿠버네티스는 지정한 이미지를 실행하고 선언한 상태를 유지할 뿐, 모델이 맞는지는 판단하지 않습니다. 잘못된 모델을 선언해도 배포는 정상으로 보여요.
Deployment→ ReplicaSet → Pod작업장

"이 이미지로 Pod를 몇 개 띄워라"를 선언하고 버전 교체까지 관리하는 객체.

비유
작업 지시서. Deployment(지시서) → ReplicaSet(인원 유지 담당 조장) → Pod(작업자) → 컨테이너(작업자가 돌리는 기계) 순서로 관리합니다.
왜 필요해
Pod를 직접 만들면 죽었을 때 아무도 다시 만들지 않습니다. Deployment로 선언하면 지워도 다시 생기고, 이미지를 바꾸면 새 버전 Pod로 차례로 교체돼요.
엑셀로 치면
서식 파일(.xltx)로 새 문서를 찍어 내는 것. 서식을 고치면 기존 파일을 고치는 게 아니라 새 서식으로 새 파일을 만들죠. Pod도 고쳐 쓰지 않고 새로 만듭니다.
이번 실습에서
replicas: 2, 이미지 income-api:study-v1, readiness는 /ready, liveness는 /health, CPU·메모리 requests와 limits를 지정합니다.
주의
Deployment의 selector와 Pod template의 label이 같아야 합니다. 선언 자체가 틀렸다면 재시작을 반복해도 해결되지 않아요.
Serviceport → targetPort연결

계속 바뀌는 Pod 앞에 고정된 이름과 포트를 세워, 요청을 준비된 Pod로 보내 주는 창구.

비유
담당자가 바뀌어도 그대로인 안내 창구. 창구 번호(port)로 받은 요청을 작업실 문(targetPort)으로 넘깁니다. 원문 표현대로 호스트 포트는 건물 출입구, Service 포트는 안내 창구, targetPort는 작업실 문이에요.
왜 필요해
Pod는 새로 만들어질 때마다 주소가 바뀝니다. 특정 Pod 주소를 적어 두면 교체되는 순간 끊겨요.
엑셀로 치면
이름 관리자의 "이름 정의". 셀 주소 대신 이름으로 참조하면 범위가 옮겨져도 수식이 따라가죠. selector는 그 이름이 가리킬 행을 고르는 필터 조건입니다.
이번 실습에서
selector app: income-api, port: 80 → targetPort: 8000. kubectl port-forward service/income-api 18080:80으로 점검합니다.
주의
Service가 만들어졌다고 요청 경로가 정상인 건 아닙니다. selector와 label 일치, EndpointSlice에 대상이 있는지, targetPort와 앱 포트가 맞는지 차례로 확인해요.
CI/CDContinuous Integration / Delivery자동 배송

코드를 바꾸면 자동으로 검사하고 이미지를 만들고(CI), 검증된 버전을 운영 환경에 반영하는(CD) 흐름.

비유
출고 라인. 신제품 설계가 들어오면 품질 검사와 포장(CI)을 거쳐 물류 창고(레지스트리)에 넣고, 매장 진열 설계도(Git 배포 설정)를 고치면 감독(Argo CD)이 매장을 설계도대로 맞춥니다(CD).
왜 필요해
사람이 손으로 배포하면 실수와 권한 문제가 남고 "지금 운영에 뭐가 떠 있지?"에 답하기 어렵습니다. 커밋 → 이미지 → 배포 설정이 이어지면 운영 중인 서비스에서 원래 코드까지 거슬러 갈 수 있어요.
엑셀로 치면
파일을 저장할 때마다 검사 매크로가 자동으로 돌고, 통과하면 공유 폴더의 배포본이 갱신되는 구조.
이번 실습에서
책은 GitLab CI(검사·빌드)와 Argo CD(GitOps 배포)를 씁니다. 이 글의 실습은 CI/CD 없이 손으로 배포하는 데까지만 해요.
주의
Argo CD의 Synced와 Healthy는 선언과 자원 상태가 맞다는 신호일 뿐 모델 품질 승인이 아닙니다. latest 태그만 덮어쓰면 Git은 그대로인데 실제 이미지가 바뀌는 일도 생겨요.
Prometheus · Grafana수집 · 시각화계기판

Prometheus는 앱이 내보이는 숫자를 주기적으로 모아 저장하고, Grafana는 그 숫자로 대시보드를 그립니다.

비유
Prometheus는 계량기를 돌며 숫자를 적어 가는 검침원, Grafana는 그 기록으로 만든 상황판, Alertmanager는 이상할 때 담당자에게 연락하는 경보 담당입니다.
왜 필요해
요청이 몇 개 오는지, 얼마나 느린지, 오류가 얼마나 나는지 알아야 사용자보다 먼저 문제를 발견합니다.
엑셀로 치면
일정 간격마다 값이 한 줄씩 쌓이는 기록 시트(Prometheus)와, 그 시트로 만든 피벗 차트 대시보드(Grafana). p95는 PERCENTILE.INC(응답시간, 0.95)와 같은 뜻이에요.
이번 실습에서
sum(rate(http_requests_total{job="income-api"}[5m]))로 최근 5분 평균 초당 요청 수를, 5xx 증가율을 전체 증가율로 나눠 오류율을 봅니다.
주의
요청 수, 오류율, 응답 시간이 정상이어도 예측이 맞는지는 모릅니다. 대시보드가 비었다고 요청이 없었다고 단정하지 마세요. 수집이 실패했을 수도 있어요.

03장에서 가장 많이 막히는 곳이 포트입니다. 번호가 세 군데에 나오고, 하나만 어긋나도 요청이 도착하지 않아요.

경로 1 Docker로만 실행할 때

docker -p

경로 2 쿠버네티스에서 점검할 때
18080내 PC 출입구
port-forward

targetPort

창구가 있다고 작업실이 자동으로 생기지는 않습니다. 앱이 8000번 문에서 기다리는데 창구가 8001번으로 안내하면 요청은 길을 잃어요. 그리고 앱은 0.0.0.0(모든 문)에 바인딩해야 바깥에서 들어온 요청을 받을 수 있습니다.

헷갈리는 짝

원문이 "둘은 다르다"고 짚은 것들입니다. 03장의 핵심 메시지는 결국 성공의 종류가 여러 개라는 거예요.

이미지 ↔ 컨테이너

포장이 끝난 밀키트. 읽기 전용 배포 단위.

밀키트를 뜯어 조리 중인 한 그릇. 실행 중인 인스턴스.

핵심이미지 하나로 컨테이너를 여러 개 띄워도 메모리와 상태는 서로 별개입니다.

RUN ↔ CMD · ENTRYPOINT

이미지를 만드는 동안 실행. 패키지 설치 같은 일.

컨테이너가 시작될 때 실행. 앱 서버 기동 같은 일.

핵심빌드가 성공해도 API가 정상 기동한다는 보장은 없습니다.

tag ↔ digest

상자에 붙인 포스트잇. 다른 상자로 옮겨 붙일 수 있음. 예: latest

상자 내용물의 지문. 내용이 바뀌면 반드시 달라짐.

핵심"latest를 배포했다"는 기록으로는 실제로 무엇이 떴는지 알 수 없습니다.

호스트 포트 ↔ 컨테이너 포트

내 PC의 출입구. 브라우저는 여기로 요청.

컨테이너 안에서 앱이 기다리는 문.

핵심이미지에 포트를 선언, 앱이 그 포트로 실행, 바깥 포트 연결은 서로 다른 설정입니다.

Service port ↔ targetPort

Service 안내 창구 번호. 클러스터 안에서 부르는 번호.

Pod 안 앱이 실제로 듣는 문 번호.

핵심containerPort 선언만으로 포트가 열리지 않습니다. targetPort가 앱의 실제 포트와 맞아야 해요.

0.0.0.0 ↔ 127.0.0.1

앱이 "모든 문에서 받겠다"는 바인딩 설정. 목적지 주소가 아님.

"나 자신". 내 PC에서 접속할 때 브라우저에 쓰는 주소.

핵심앱이 127.0.0.1에만 바인딩돼 있으면 포트를 연결해도 바깥 요청이 못 들어옵니다.

Running ↔ Ready

프로세스가 떠 있다. 작업자가 출근했다.

요청을 받을 준비가 됐다. 업무를 시작했다.

핵심Running이어도 Ready가 아니면 Service가 요청을 보내지 않습니다.

readiness ↔ liveness

트래픽 대상에서 잠시 빠짐. 재시작은 안 함.

컨테이너를 재시작함.

핵심외부 시스템이 느리다고 liveness를 실패시키면 재시작이 부하를 더 키울 수 있습니다.

Docker로 빌드 ↔ 런타임으로 실행

Docker로 이미지를 만듦.

노드에서는 containerd나 CRI-O가 실행하는 경우가 많음.

핵심Docker로 빌드했다고 노드도 Docker Engine으로 실행한다는 뜻은 아닙니다.

CI ↔ CD

변경을 검사하고 이미지를 만드는 통합 과정.

검증된 변경을 운영 환경에 전달하고 배포하는 과정.

핵심책임을 나눠야 "어떤 검사를 통과한 버전이 운영에 있나"를 설명할 수 있습니다.

Synced ↔ Healthy

클러스터 명세가 Git 선언과 일치.

자원 종류별 상태 판단이 정상.

핵심틀린 모델 버전을 Git에 적어도 둘 다 초록불일 수 있습니다.

ConfigMap ↔ Secret

일반 설정. 벽에 붙인 안내문.

비밀번호, 토큰 같은 민감한 설정. 잠긴 서랍.

핵심Secret의 기본 인코딩은 암호화가 아닙니다. 접근 권한과 저장 보호가 따로 필요해요.

Counter ↔ Gauge

누적만 되는 값. 요청 수, 오류 수. 엑셀의 누적 합계 열.

오르내리는 현재 값. 메모리, 대기 작업. 지금 잔액 셀.

핵심Counter가 10,000이어도 지금 바쁘다는 뜻이 아닙니다. 구간 증가율(rate)을 봐야 해요.

배포 성공 ↔ 예측 품질

배포 성공

이미지 생성, Pod 실행, 요청 연결, 메트릭 정상.

예측 품질

모델이 맞는 답을 내는지. 데이터 변화와 실제 정답으로만 확인.

핵심이게 04장에서 MLflow와 Feast를 붙이는 이유입니다.

용어 사전

원문에 나오는 용어를 구역별로 모았습니다. 항목을 누르면 비유, 필요한 이유, 실습에서 쓰이는 곳이 펼쳐져요.

실습 순서와 등장 용어

모델 없는 작은 API로 이미지와 네트워크 문제를 먼저 분리해 보는 실습입니다. 칩을 누르면 해당 용어로 이동해요.

  1. 앱 만들고 단독 실행

    /, /health, /ready 세 경로가 있는 FastAPI 앱을 만들고, Docker 없이 uvicorn으로 띄워 /docs에서 Execute를 눌러 봅니다.

    확인 Server response 200, "status": "ready"

  2. 이미지로 포장하고 로컬 실행

    필요한 두 파일만 COPY하는 Dockerfile을 쓰고, docker build 후 docker run -p 127.0.0.1:18000:8000으로 띄웁니다.

    확인 curl.exe http://127.0.0.1:18000/에 v1 응답

  3. Deployment와 Service 적용

    context를 확인하고, minikube image load로 이미지를 넣은 뒤 Namespace를 만들고 kubectl apply. rollout 상태와 EndpointSlice를 보고 port-forward로 점검합니다.

    확인 curl.exe http://127.0.0.1:18080/에 v1 응답

  4. 일부러 고장 내 보기

    이미지 태그, selector, readiness 경로, targetPort를 하나씩 바꿔 증상과 증거가 어디에 나타나는지 봅니다.

    확인 증상마다 다른 곳(Events, EndpointSlice, Ready 조건)에 단서가 남음

  5. 메트릭 읽고 정리

    PromQL로 초당 요청 수와 오류율을 읽고, 끝나면 kubectl delete -f deployment.yaml로 이 예제만 지웁니다.

    확인 트래픽 없음과 수집 실패를 "오류율 0%"와 구별
