핵심 6

질문하신 kind, GitOps, Argo CD, KFP와 04장의 두 주인공 MLflow, Feast입니다. 이 여섯 개만 잡히면 나머지는 거의 부품 이름이에요.

kindKubernetes IN Docker공장 부지

내 PC의 Docker 안에 연습용 쿠버네티스 클러스터를 만드는 도구.

비유
진짜 공장 부지를 사는 대신, 방 안에 실제로 돌아가는 미니어처 공장을 차리는 것. 기계 구조와 규칙은 진짜와 같고 크기만 작습니다.
왜 필요해
쿠버네티스는 원래 서버 여러 대가 필요합니다. kind를 쓰면 노트북 한 대로 연습하고, 망가지면 지우고 다시 만들 수 있어요.
엑셀로 치면
원본은 그대로 두고 연습용 사본 파일을 만들어 마음껏 고쳐 보는 것.
이번 실습에서
book-env라는 kind 클러스터에 KFP, MLflow, 저장소, PostgreSQL, Redis를 올립니다. python bookenv.py up으로 만들고 down으로 지워요. 책은 k3s나 MicroK8s를 씁니다.
주의
kind는 PC와 분리된 별도 컴퓨터처럼 움직입니다. PC에서 만든 이미지도 bookenv.py load로 안에 넣어 줘야 쓸 수 있어요.
GitOpsGit + Operations공장 짓기

Git에 적힌 설정을 정답으로 삼는 운영 방식. 서버를 손으로 바꾸지 않고 Git의 설정 파일을 고치면 서버가 그대로 따라갑니다.

비유
매장 배치를 바꿀 때 현장 직원이 즉흥적으로 옮기지 않고, 본사 설계도를 고치면 시공팀이 설계도대로 맞추는 방식. 설계도에는 수정 이력이 남습니다.
왜 필요해
누가 언제 무엇을 바꿨는지 Git에 남고, 문제가 생기면 이전 설계도로 되돌리면 됩니다. 손으로 고친 설정이 쌓여 아무도 이유를 모르는 상태가 되는 걸 막아요.
엑셀로 치면
공유 폴더의 원본 서식 파일만 고치고, 각 부서 파일은 원본을 따라 자동으로 바뀌게 하는 규칙.
이번 실습에서
책 부록 A가 이 방식으로 Kubeflow를 설치합니다. 이 실습은 GitOps 없이 bookenv.py 스크립트로 직접 설치해요.
주의
GitOps는 도구 이름이 아니라 방식입니다. 그 방식을 실제로 해 주는 도구가 Argo CD예요.
Argo CDArgo Continuous Delivery공장 짓기

GitOps를 실행하는 도구. Git의 설정과 클러스터의 실제 상태를 계속 비교하고, 다르면 Git 쪽에 맞춥니다(동기화).

비유
설계도를 들고 현장을 순찰하는 건설 감독. 설계도와 다른 곳을 찾으면 설계도대로 고쳐 놓습니다.
왜 필요해
Kubeflow처럼 부품이 수십 개인 시스템을 한 번에 설치하고, 이후에도 설계도와 어긋나지 않게 유지할 수 있어요.
이번 실습에서
책은 kubectl apply -k argocd/로 Argo CD를 먼저 설치하고 kubectl apply -f kubeflow.yaml을 실행합니다. 그러면 Argo CD가 Kubeflow 구성 요소별 Application을 배포하고 동기화해요. 이 실습 환경에는 Argo CD가 없습니다.
주의
Argo Workflows와 이름만 비슷하고 하는 일이 다릅니다. Kubeflow를 설치한다고 Argo CD가 자동으로 생기지도 않아요.
KFPKubeflow Pipelines생산 라인

머신러닝 작업을 여러 단계로 나눠 순서대로 실행하고, 실행 기록을 남기는 도구.

비유
공장의 생산 라인. ① 주문서(예측 대상) 읽기 → ② 재료(피처) 받기 → ③ 공식 레시피(모델)로 만들기 → ④ 창고에 넣기. 작업대마다 다른 작업자(Pod)가 서 있고, 결과물은 상자(파일)에 담아 다음 작업대로 넘깁니다.
왜 필요해
노트북 셀을 손으로 누르면 순서를 틀리기 쉽고 기록도 남지 않습니다. KFP는 단계와 순서를 정해 두고 매번 같은 방식으로 돌리며, 어느 단계에서 실패했는지 화면에 보여 줘요.
엑셀로 치면
파워 쿼리의 "적용된 단계". 단계를 정해 두면 새로 고칠 때마다 같은 순서로 처리됩니다. 다른 점은 단계마다 다른 작업자가 일한다는 것.
이번 실습에서
kind에 KFP 2.4.1만 단독 설치하고, 4단계 배치 추론 파이프라인을 돌려 income_predictions.parquet를 만듭니다.
주의
5장 파이프라인은 학습을 하지 않습니다. 4장에서 등록한 모델과 Feast 정의를 가져다 예측만 해요. 그래서 MLflow와 Feast 단계를 먼저 끝내야 합니다.
MLflow실험 기록과 모델 보관연구실

모델 실험을 기록하고, 고른 모델을 이름과 버전으로 보관하는 도구. 학습 알고리즘이 아닙니다.

비유
연구실의 실험 노트와 공식 레시피 금고. 어떤 설정으로 몇 번 구웠고 맛 점수가 몇 점이었는지 적고, 가장 좋은 레시피를 "공식 레시피 v1"로 금고에 넣습니다.
왜 필요해
어떤 데이터와 설정으로 만든 모델인지 나중에 찾을 수 있고, 다른 프로그램이 이름만으로 그 모델을 꺼내 쓸 수 있어요.
엑셀로 치면
"보고서_최종_진짜최종_v3.xlsx" 대신, 파일 이름은 하나로 두고 버전 번호와 작성 조건이 자동으로 기록되는 것.
이번 실습에서
실험 income-classifier에 run 4개를 기록하고, 가장 좋은 Random Forest(ROC AUC 0.855)를 random-forest-classifier 버전 1로 등록해 Production으로 지정합니다.
주의
기록 정보는 PostgreSQL에, 모델 파일은 S3에 있습니다. MLflow 화면이 열려도 S3 연결이 끊기면 모델을 받을 수 없어요.
FeastFeature Store재료실

모델에 넣을 피처(입력값)를 정의하고, 학습과 예측 때 같은 기준으로 꺼내 주는 피처 스토어.

비유
재료실. "손님 42번 재료를 5월 22일 기준으로 주세요" 하면 그날 있던 재료를 내줍니다. 계산대 옆 냉장고(Redis)에는 바로 꺼낼 최신 재료를 따로 둬요.
왜 필요해
학습 때와 예측 때 피처를 다르게 만들면 같은 모델도 엉뚱한 답을 냅니다. 과거 시점을 예측하는데 최신값을 쓰면 미래 정보가 섞여요.
엑셀로 치면
user_id를 기준키로 여러 시트의 열을 붙이는 VLOOKUP인데, 날짜 기준까지 맞춰 주는 VLOOKUP.
이번 실습에서
Entity user_id와 FeatureView 3개(demographic, relationship, occupation)를 등록하고 과거 조회와 온라인 조회를 해 봅니다. 5장 파이프라인의 2단계가 Feast로 피처를 가져와요.
주의
MLflow는 "어떤 모델을 만들었나", Feast는 "모델이 쓸 피처를 어디서 어떤 기준으로 가져오나"를 맡습니다. 책의 학습 노트북은 CSV를 직접 읽고 Feast를 거치지 않아요.

헷갈리는 짝

원문이 일부러 "둘은 다르다"고 짚은 것들입니다. 실습 중 막히는 곳은 대부분 여기서 나와요.

Argo CD ↔ Argo Workflows

공장을 설계도대로 짓고 유지하는 건설 감독. 설치·배포 담당.

생산 라인에서 작업자를 순서대로 부르는 반장. KFP의 실행 엔진.

핵심KFP를 깔면 Argo Workflows는 따라오지만, Argo CD는 따로 설치해야 합니다.

Kubeflow ↔ KFP

대시보드, 노트북, 인증, Istio, Pipelines까지 든 종합 세트.

그중 파이프라인 부분. 단독 설치(standalone)도 됩니다.

핵심책은 Kubeflow 전체, 이 실습은 KFP만 씁니다.

MLflow 실험 ↔ KFP 실험

학습 run을 묶습니다. "어떤 모델을 만들었나".

파이프라인 실행을 묶습니다. "생산 라인을 언제 돌렸나".

핵심둘 다 이름이 income-classifier지만 서로 아무 관계가 없습니다.

feast apply ↔ materialize

재료 목록표(정의)를 대장(Registry)에 등록. 재료는 안 옮깁니다.

실제 값을 냉장고(Redis)에 채워 넣기.

핵심Registry에 FeatureView가 보여도 Redis에 값이 있다는 뜻은 아닙니다.

과거 시점 조회 ↔ 온라인 조회

큰 창고에서 기준 시각의 "그때 값"을 찾기. 학습과 과거 날짜 배치 예측용.

냉장고(Redis)에서 최신값을 빠르게. 실시간 예측용.

핵심5장 배치 추론은 과거 시각 기준이라 get_historical_features()를 씁니다.

localhost ↔ 클러스터 서비스 주소

"나 자신". PC에서 쓰면 PC, Pod 안에서 쓰면 그 Pod.

이름.구역.svc.cluster.local. 공장 어디서 걸어도 같은 곳으로 가는 내선번호.

핵심PC는 포트포워딩 터널로, Pod는 서비스 주소로 접속합니다.

파라미터 ↔ 아티팩트

지시서에 적는 짧은 값. 모델 이름, 버킷 이름.

다음 작업대로 보내는 파일. 대상 목록, 피처 표, 예측 결과.

핵심Pod끼리 메모리를 공유하지 않아서 큰 데이터는 파일로 넘깁니다.

컴파일 ↔ 실행

파이썬 정의를 YAML 지시서로 옮겨 적기. 아직 아무것도 돌지 않습니다.

지시서대로 Pod가 뜨고 실제 데이터를 읽습니다.

핵심이미지 이름, 주소, 권한 문제는 실행해 봐야 드러납니다.

Production 지정 ↔ 배포

MLflow에서 "이 버전이 공식"이라는 꼬리표를 붙이는 일.

배포

모델을 API 서버로 띄워 요청을 받게 하는 일.

핵심꼬리표를 붙여도 서버는 뜨지 않습니다. 5장 파이프라인이 꼬리표로 모델을 찾을 뿐이에요.

PC의 이미지 ↔ kind 안의 이미지

docker build로 내 PC에 만든 도시락.

공장 안으로 반입한 도시락. Pod는 이것만 씁니다.

핵심다시 빌드하면 bookenv.py load로 다시 넣어야 합니다. 안 넣으면 ErrImageNeverPull.

MinIO ↔ SeaweedFS

책이 쓰는 S3 방식 창고. 콘솔 로그인 minio / minio123.

이 실습이 대신 넣은 창고. 웹 화면은 로그인 없는 Filer.

핵심서비스 이름과 계정을 그대로 둬서 책 코드는 고치지 않아도 됩니다.

실행 성공 ↔ 예측 품질

실행 성공

네 단계가 모두 초록 체크. 파일이 끝까지 전달됐다는 뜻.

예측 품질

예측이 맞는지, 누구의 예측인지, 임계값이 적절한지.

핵심책 코드의 결과에는 user_id가 빠져 있습니다. 초록 체크는 품질 보증이 아니에요.

용어 사전

원문에 나오는 용어를 공장 구역별로 모았습니다. 항목을 누르면 비유, 필요한 이유, 이번 실습에서 쓰이는 곳이 펼쳐져요.

실습 순서와 등장 용어

원문의 A~E 순서입니다. 앞 단계가 끝나야 다음 단계가 돌아가요. 칩을 누르면 해당 용어로 이동합니다.

  1. 환경과 버킷 준비

    kind 클러스터에 KFP, 저장소, PostgreSQL, Redis, MLflow를 설치하고, 포트포워딩을 켠 뒤 버킷 다섯 개를 만듭니다.

    끝나면 남는 것 서비스들과 버킷 다섯 개, 그리고 KFP가 만든 mlpipeline

  2. MLflow로 학습과 모델 등록

    노트북에서 데이터를 S3에 올리고 모델 세 개를 학습해 기록한 뒤, 가장 좋은 모델을 등록하고 Production으로 지정합니다.

    끝나면 남는 것 실험 income-classifier, 모델 random-forest-classifier의 Production 버전

  3. Feast로 피처 정의와 조회

    피처 원천 파일을 올리고 정의를 등록(apply)한 뒤, 과거 시점 조회와 온라인 적재(materialize), 온라인 조회를 해 봅니다.

    끝나면 남는 것 원천 parquet, 로컬용 Registry, Redis의 온라인 피처

  4. KFP로 배치 추론

    이미지를 빌드해 kind에 넣고, Job으로 클러스터용 Registry를 만든 뒤 파이프라인을 컴파일, 업로드, 실행합니다.

    끝나면 남는 것 클러스터용 Registry와 설정, 파이프라인 실행 기록

  5. 결과 확인과 정리

    예측 파일이 업무용 버킷에 저장됐는지 보고, 실패했다면 해당 단계의 Logs부터 확인합니다.

    끝나면 남는 것 inference-datasets/income_predictions.parquet
