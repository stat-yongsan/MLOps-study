오케스트레이션orchestration생산 관리

여러 단계를 정해진 순서로 실행하면서, 단계마다 필요한 데이터와 컴퓨팅 자원을 갖춰 주는 일. Kubeflow에서는 KFP가 맡습니다.

비유
공장장. 어떤 작업대를 어떤 순서로 돌릴지, 작업자(Pod)를 언제 부를지, 상자를 어디에 둘지 정합니다.
왜 필요해
추론 흐름(읽기 → 피처 붙이기 → 예측 → 저장)은 정해진 주기로 반복되고, 매번 날짜나 테이블 이름만 바뀝니다. 사람이 순서대로 돌리면 빠뜨리기 쉬워요.
엑셀로 치면
"기준일" 셀만 바꾸면 매크로가 데이터 가져오기 → 가공 → 계산 → 저장을 차례로 돌리는 보고서 자동화.
이번 장에서
4장에서 손으로 잇던 MLflow와 Feast를 KFP 파이프라인 하나로 묶어, 읽기부터 저장까지 한 번에 돌립니다.
주의
KFP는 단계와 순서를 관리할 뿐, 모델을 학습하거나 고르지 않습니다. 이 파이프라인은 4장에서 등록한 모델로 예측만 해요.
컴포넌트component작업대

파이프라인의 단계 하나. Python 코드 → Docker 이미지 → component.yaml 순서로 만들고, 실행할 때 Pod 하나에서 따로 돕니다.

비유
작업대 하나. 작업 매뉴얼(코드), 작업자가 들고 오는 공구·재료 키트(이미지), 작업대 앞 안내판(component.yaml)이 한 세트입니다.
왜 필요해
기능 하나씩 나눠야 다른 파이프라인에서 다시 쓰고, 나눠 맡고, 따로 테스트할 수 있어요.
엑셀로 치면
인수를 받는 매크로(Sub) 하나. 매크로마다 한 가지 일만 하게 나누면 다른 파일에서도 불러 쓸 수 있죠.
이번 장에서
read_data, retrieve_features, run_inference, write_data 네 개. ken-0913님은 책의 src/*.py를 한 줄도 고치지 않고 연결 방식만 바꿨습니다.
주의
책은 이미지 이름을 넷으로 나누지만, Dockerfile이 저장소 전체를 복사해서 네 이미지의 내용은 모두 같아요.
component.yaml컴포넌트 명세작업대

컴포넌트의 입력과 출력, 타입, 실행할 이미지와 명령을 적은 명세. KFP는 코드 대신 이 안내판을 보고 값을 채우고 상자를 연결합니다.

비유
작업대 안내판. "받는 것: 버킷 이름(메모), 앞 작업대의 상자(선반 위치) / 내놓는 것: 상자 하나 / 실행: 이 키트로 이 명령".
왜 필요해
값을 넣는 자리와 파일을 주고받는 자리를 구분해 적어 둬야, KFP가 실행할 때 알맞은 값과 경로를 채울 수 있어요.
엑셀로 치면
함수의 인수 목록. =VLOOKUP(찾을값, 범위, 열번호, 일치)처럼 무엇을 어떤 자리에 넣는지 정해 둔 틀.
이번 장에서
inputValue는 문자열 값을 그대로, inputPath와 outputPath는 KFP가 파일 경로를 채워 넣는 자리예요. 아래 직접 해 보기에서 채워지는 모습을 볼 수 있어요.
주의
컴포넌트끼리 데이터를 주고받게 하는 건 inputPath와 outputPath입니다. 타입을 Dataset으로 적어도 열 이름이나 결측은 검사해 주지 않아요.
파이프라인과 DAG@dsl.pipeline생산 관리

@dsl.pipeline 함수 안에서 태스크를 만들고 앞 태스크의 출력을 다음 태스크 입력으로 넘기면, KFP가 그 참조를 보고 실행 순서(DAG)를 정합니다.

비유
공정 순서도. 화살표 하나가 "이 상자가 나와야 다음 작업대가 시작"을 뜻해요. DAG는 방향이 있고 되돌아가는 고리가 없는 순서도라는 뜻입니다.
왜 필요해
순서를 따로 적지 않아도, 데이터가 흐르는 방향이 곧 실행 순서가 됩니다.
엑셀로 치면
계산 순서. B1에 =A1*2가 있으면 엑셀은 A1부터 계산하죠. task.outputs["data_output"]을 넘기는 게 셀 참조와 같아요.
이번 장에서
retrieve_features_task는 fetch_data_task.outputs["data_output"]을 받으므로 read_data가 끝난 뒤 실행됩니다. 함수 전체를 compiler.Compiler().compile()로 YAML로 바꿔 올려요.
주의
출력 참조로 잇지 않은 태스크끼리는 순서가 정해지지 않아 동시에 돌 수 있습니다.
파이프라인 파라미터runtime parameter생산 관리

@dsl.pipeline 함수의 인자. 실행할 때마다 값을 바꿀 수 있는 런타임 파라미터가 됩니다.

비유
매번 라인에 꽂는 주문서. 라인은 그대로 두고 주문서(버킷, 파일 이름, 모델 이름, stage)만 바꿉니다.
왜 필요해
코드를 고치지 않고 다른 날짜, 다른 테이블, 다른 모델로 돌릴 수 있어요. 주소를 하드코딩하지 않는 게 설계 원칙(파라미터화)입니다.
엑셀로 치면
보고서 상단의 입력 셀(기준일, 부서). 이 셀만 바꾸면 아래 수식이 전부 다시 계산되죠.
이번 장에서
minio_host, entity_df_bucket, feature_list, model_name, model_stage, mlflow_host, output_bucket 등 14개. 주소는 Pod 기준이라 localhost를 쓰면 안 돼요.
주의
책은 access_key, secret_key도 파라미터로 넘겨서 실행 기록(UI와 DB)에 평문으로 남습니다. 두 분 모두 이 둘을 빼고 Secret으로 넣었어요.
아티팩트 저장소pipeline root창고

단계 사이에 넘기는 중간 데이터(Dataset)와 로그를 쌓아 두는 저장소. 다음 단계는 여기서 읽어 갑니다.

비유
작업대 사이 임시 선반. 작업자(Pod)는 일이 끝나면 퇴근하니, 결과를 선반에 두고 가야 다음 작업자가 가져갑니다.
왜 필요해
Pod끼리 메모리를 공유하지 않아요. 파일로 남겨야 이어지고, 나중에 단계별 결과와 로그를 다시 볼 수 있습니다.
엑셀로 치면
매크로 단계마다 결과를 임시 시트에 붙여 두고, 다음 단계가 그 시트를 읽는 것.
이번 장에서
책은 KFP에 딸린 MinIO, ken-0913님은 RustFS의 mlpipeline 버킷, kurtyoon님은 공용 SeaweedFS의 mlpipeline 버킷을 씁니다.
주의
KFP 2.17.3은 함께 설치하는 SeaweedFS 주소를 여러 곳의 기본값으로 써서, 저장소를 바꾸려면 네 곳을 모두 고쳐야 했어요.

헷갈리는 짝

  
두 글이 "둘은 다르다"고 짚은 것들입니다. 위쪽은 파이프라인, 아래쪽은 실습 환경 이야기예요.

  

    
컴포넌트 ↔ 태스크

      

        
fetch_data_op. component.yaml로 불러온 작업대 설계.

        
fetch_data_task. 그 설계로 오늘 라인에 놓은 작업대 하나.

      
핵심엑셀의 함수 정의와, 셀에 그 함수를 한 번 쓴 것의 차이예요.

    
inputValue ↔ inputPath · outputPath

      

        
문자열 값이 그대로 명령줄에 들어감. 지시서 메모.

        
KFP가 파일 경로를 채움. 선반 위치 번호.

      
핵심작업대끼리 상자를 주고받는 길은 경로 자리뿐입니다.

    
UI에 올려 실행 ↔ SDK로 바로 실행

      

        
Upload pipeline → Experiment → Create run → 파라미터 입력 → Start.

        
create_run_from_pipeline_package로 컴파일과 실행을 한 번에.

      
핵심SDK로 돌리면 Pipelines 메뉴엔 안 보이고 Experiments 아래에만 Run이 쌓여요.

    
stage ↔ alias

      

        
"Production" 같은 상태 꼬리표. 책 코드가 이걸로 모델을 찾음.

        
자유 이름표. MLflow 3에서 권장하는 방식.

      
핵심책 코드를 쓰려면 stage를 지정해야 하고, MLflow 3.16 화면에서 Stage 열을 보려면 새 UI 토글을 꺼야 해요.

    
실행 성공 ↔ 올바른 예측

      

        
실행 성공
네 단계 모두 초록 체크.

        
배치에 빠진 범주가 있으면 다른 열이 지워져 조용히 틀릴 수 있음.

      
핵심위 "오류 없이 틀리는 원-핫 인코딩"에서 직접 확인할 수 있어요.

    
Redis에 접속 안 함 ↔ feast[redis]는 설치

      

        
5장 파이프라인은 온라인 저장소에 연결하지 않음.

        
설정에 type: redis가 있으면 검증하느라 모듈을 불러옴.

      
핵심"안 쓰니까 설치 안 해도 된다"가 통하지 않아서 ken-0913님 첫 실행이 실패했어요.

    
latest 태그 ↔ 커밋 SHA 태그

      

        
같은 이름이면 노드가 새 이미지를 안 받을 수 있음.

        
커밋마다 이름이 달라 항상 새로 받음.

      
핵심IfNotPresent 정책 때문에 ken-0913님은 매니페스트에 latest를 두지 않았어요.

    
파라미터로 키 넘기기 ↔ Secret 환경 변수

      

        
파라미터 (책)
실행 기록에 키가 평문으로 남음.

        
컴파일된 YAML에는 Secret 이름만 들어감.

      
핵심막는 건 "기록에 키가 남는 일"이에요. 파이프라인을 올릴 수 있는 사람은 그 Secret도 읽을 수 있어요.

    
이미지 이름 넷 ↔ 내용은 하나

      

        
이름
read-minio-data, retrieve-feast-features, run-inference, write-minio-data.

        
Dockerfile이 저장소 전체를 복사해서 모두 같음.

      
핵심같은 층이라 두 번째 단계부터는 이미지 받는 데 2~4초면 끝나요.

    
배치 추론 ↔ 실시간 서빙

      

        
모아 둔 대상을 한꺼번에. KFP가 잘 맞음.

        
요청마다 바로 답함. 6장 BentoML.

      
핵심5장은 배치, 6장은 실시간입니다.

    
Kubeflow 전체 ↔ 필요한 것만

      

        
Kubeflow 1.7 전체
Istio, Dex, Notebooks, Katib까지. 약 3.9코어.

        
MLflow, 저장소, Valkey, KFP. 실습 쪽 합계 약 1코어.

      
핵심대신 사용자 간 격리가 없고 클러스터 안 통신은 암호화되지 않는 한계를 받아들였어요.

    
공개 주소 ↔ 클러스터 안 주소

      

        
authentik 로그인을 거쳐야 들어감.

        
로그인 없음. NetworkPolicy가 누가 닿을지 정함.

      
핵심같은 MLflow를 문 두 개로 열고, 문마다 지키는 방식이 달라요.

    
forward auth ↔ OIDC

      

        
정문이 대신 출입증 확인. 로그인 기능 없는 앱(MLflow, KFP)에.

        
앱이 직접 발급소에 확인. Argo CD, Grafana, Gitea.

      
핵심앱이 로그인을 지원하느냐에 따라 고릅니다.

    
S3에 직접 쓰기 ↔ MLflow 아티팩트 프록시

      

        
직접 쓰기
노트북과 Pod마다 S3 키가 필요.

        
MLflow 서버가 자기 키로 대신 저장. 손님은 키가 필요 없음.

      
핵심그래서 kurtyoon님 환경의 추론 단계는 S3 키 없이 모델을 받아요.

    
4장 레지스트리 ↔ 5장 레지스트리

      

        
registry_local.db
노트북에서 apply. 노트북 기준 주소가 적힘.

        
클러스터 안 Job으로 apply. Pod가 닿는 주소가 적힘.

      
핵심레지스트리에는 데이터 위치 주소가 같이 저장돼서, 쓰는 곳이 다르면 따로 만들어야 해요.

    
Redis ↔ Valkey

      

        
Redis
책과 다른 정리들이 쓰는 냉장고.

        
Redis와 같은 말을 알아듣는 오픈소스 냉장고.

      
핵심Feast의 Redis 클라이언트를 고치지 않고 그대로 쓸 수 있어요.

    
amd64 ↔ arm64

      

        
amd64
일반 PC·서버. ken-0913님 KFP Pod가 도는 곳.

        
kurtyoon님 노드. amd64 전용 이미지는 그냥은 안 돎.

      
핵심MLMD와 Feast 서버 이미지가 amd64 전용이라 kurtyoon님은 다른 길을 찾아야 했어요.

막힌 곳과 푼 방법

  

    
피처 조회 단계 실패 (1분 32초)

      
증상
FeastModuleImportError: redis 모듈을 불러올 수 없음.

      
해결
feast[aws]를 feast[aws,redis]로 바꿔 설치.

    
추론 단계가 로그 없이 멈춤 (12분 15초)

      
증상
MLflow 서버 로그에 요청이 오지 않음. MLflow Service에 엔드포인트가 없었음.

      
원인
노드 재기동 뒤 Postgres보다 먼저 뜬 MLflow Pod의 init 컨테이너가 재시도 간격을 약 8시간까지 늘린 채 대기.

      
해결
kubectl rollout restart로 MLflow 재기동, 멈춘 Run은 Terminate.

    
책 저장소를 그대로 쓰면

      
이미지
python:3.10-slim-buster는 지원 종료로 빌드 실패, 저자 계정 varunmallya/*:latest.

      
모델
4장에서 stage를 지정하지 않아 Production 모델을 못 찾음.

      
레지스트리
책 4장 레지스트리는 localhost를 가리킴.

      
키
파이프라인 파라미터라 실행 기록에 평문 저장.

      
SDK
저장소 YAML은 kfp 2.9.0으로 컴파일됨.
