01장 용어를 공장으로 풀어 보기

01장은 시제품 한 번 잘 만들기와 공장을 계속 돌리기가 왜 다른지 보여 주는 장입니다. 핵심은 완성품(모델)에서 재료(데이터)와 제조 이력(코드, 설정)까지 거슬러 올라갈 수 있어야 한다는 것이에요.

용어 이름을 누르면 설명으로 이동하고, 좌표 변환기와 해시 실험은 값을 바꿔 직접 해 볼 수 있습니다.

핵심 6

01장의 뼈대입니다. 고리(생애주기), 이력(계보), 공용 주방(플랫폼), 어긋남(학습·서빙 불일치), 나누기(분할), 출고 확인서(출시 명세).

ML 생애주기실험 → 운영생애주기

문제 정의부터 데이터, 학습, 평가, 배포, 개선까지 잇는 지도. 직선으로 그려도 실제로는 앞 단계로 자주 돌아갑니다.

비유
시제품 공방과 양산 공장. 공방은 "어떤 레시피가 좋은가"를, 공장은 "그 레시피로 매일 안전하게 만들고 바꿀 수 있는가"를 묻습니다.
왜 필요해
모델을 한 번 잘 학습시키는 것과 서비스로 계속 운영하는 것은 다른 문제입니다.
엑셀로 치면
한 번 만든 분석 파일과 매달 돌아가는 보고 체계의 차이. 후자는 누가 언제 돌려도 같은 절차로 나와야 하죠.
이번 장에서
실험의 "평가 점수가 충분한가?"가 운영에서는 "실제 입력에서도 품질과 응답 시간이 유지되는가?"로 바뀝니다.
주의
지표가 나쁘면 모델뿐 아니라 데이터와 문제 정의도 다시 봅니다.
계보lineage데이터

완성품(모델)에서 재료(데이터)와 제조 이력(코드, 설정, 실행)까지 거슬러 올라가는 연결.

비유
식품의 이력 추적 번호. 문제가 생긴 제품의 번호로 어느 농장, 어느 공장, 어느 날 생산했는지 찾습니다.
왜 필요해
결과가 나쁘면 가중치 파일만으로는 이유를 알 수 없습니다. 어떤 이미지와 라벨, 분할, 전처리, 설정이었는지 함께 찾아야 해요.
엑셀로 치면
수식 탭의 "참조되는 셀 추적". 결과 셀에서 어떤 원본 셀을 거쳐 왔는지 화살표로 따라가는 것.
이번 장에서
해시 실험으로 파일 이름이 같아도 내용이 바뀌면 지문이 달라지는 걸 확인합니다.
주의
기록이 있다고 비트 단위로 같은 결과가 보장되지는 않습니다. 모델 파일 보관과 재현 가능한 상태 유지는 달라요.
ML 플랫폼ML platform플랫폼

실험, 학습, 배포, 관측을 반복하게 해 주는 공통 기반. 도구를 모아 놓은 화면이 아닙니다.

비유
여러 팀이 함께 쓰는 공용 주방. 재료 창고(피처 스토어), 실험 노트(실험 추적), 레시피 금고(모델 레지스트리), 순서표(오케스트레이션), 주문 창구(Model API), 손님 반응 관찰(모니터링).
왜 필요해
팀마다 배포와 기록 방식을 새로 만들면 반복 작업과 실수가 쌓입니다.
엑셀로 치면
부서마다 따로 만들던 보고서를 공용 템플릿, 공용 데이터 연결, 공용 매크로로 묶는 것.
이번 장에서
책은 Kubeflow Pipelines, Feast, MLflow, 컨테이너와 CI/CD를 씁니다.
주의
MLflow를 설치했다고 데이터 품질이 보장되지 않고, 원천 수집과 데이터 웨어하우스 전체를 플랫폼 책임으로 넣을 필요도 없습니다. 무엇을 받아 무엇을 주는지, 누가 운영하는지부터 정해요.
학습·서빙 불일치training-serving skew출시

학습 때와 서비스 때 입력을 다르게 처리해서 같은 모델이 다른 입력을 받게 되는 문제.

비유
시험 주방에서는 재료를 깍둑썰기했는데 매장 주방에서는 통째로 넣는 것. 레시피는 같아도 맛이 다릅니다.
왜 필요해
배포에는 가중치뿐 아니라 입력을 바꾸는 전처리와 결과를 응답으로 만드는 코드가 함께 들어갑니다.
엑셀로 치면
기준 시트는 날짜를 텍스트로, 새 시트는 날짜 형식으로 넣어서 VLOOKUP이 오류도 없이 조용히 틀리는 것.
이번 장에서
학습 때는 이미지를 일정 크기로 바꾸고 픽셀값을 정규화했는데 API는 원본을 그대로 넣는 경우.
주의
되돌릴 때도 모델만이 아니라 호환되는 전처리와 서비스 코드까지 함께 되돌려야 합니다.
데이터 분할train · validation · test데이터

학습셋은 가중치 학습, 검증셋은 모델과 설정 선택, 테스트셋은 마지막 확인. 어떻게 나누느냐도 모델의 일부입니다.

비유
연습 문제, 모의고사, 수능.
왜 필요해
같은 영상에서 뽑은 거의 같은 프레임이 학습과 테스트에 섞이면, 새 상황을 이해하는 실력보다 본 장면을 기억하는 능력을 높게 평가합니다.
엑셀로 치면
같은 고객의 행이 학습 시트와 평가 시트로 갈라지지 않게 고객 ID 단위로 나누는 것. RAND()로 섞어 행 단위로 자르면 위험할 수 있어요.
이번 장에서
동영상 A, B에서 100프레임씩 뽑았다면 촬영 세션 단위로 묶어 나눕니다. 시간 변화가 문제라면 과거로 학습하고 이후 기간으로 검증해요.
주의
묶어서 나눴다고 모든 문서 유형이 평가셋에 충분히 들어가는 건 아닙니다. 분할 후 표본 수와 유형 분포를 확인해요.
출시 명세release manifest출시

하나의 출시가 어떤 코드, 데이터, 분할, 전처리, 모델, 서버 이미지, 평가, 롤백 대상의 조합인지 적은 한 장.

비유
제품 출고 확인서. 어느 레시피 버전과 재료 묶음, 공정으로 만들었고, 문제가 생기면 어느 제품으로 교체할지 적혀 있습니다.
왜 필요해
모델만 되돌리면 호환되지 않는 전처리나 API 규격이 남을 수 있습니다. 조합 단위로 적어야 제대로 되돌릴 수 있어요.
엑셀로 치면
보고서 맨 앞의 "버전 정보" 시트. 원본 데이터 기준일, 쿼리 버전, 검토자, 이전 버전 파일 위치를 적어 두는 것.
이번 장에서
release_id, code_revision, dataset_snapshot, split_policy, preprocessing, model_uri, image_digest, evaluation_report, rollback_release.
주의
release_id는 모델 버전과 다릅니다. 모델이 그대로여도 좌표 복원 코드를 바꾸면 새 출시예요.

카드 탐지 요청 하나 따라가기

휴대전화 사진에서 신분증 카드 위치를 찾아 자르는 서비스입니다. 글자를 읽거나 진위를 판단하지는 않아요. 범위를 이렇게 좁혀야 라벨과 평가 기준도 정할 수 있습니다.

같은 상자, 다른 표현

API 응답 (x1, y1, x2, y2)(100, 160, 900, 640)
YOLO 라벨 (중심x, 중심y, 폭, 높이)(0.5, 0.5, 0.8, 0.6)

YOLO 라벨의 앞 두 값 (0.5, 0.5)을 왼쪽 위 좌표로 잘못 읽으면 사진 한가운데부터 잘라 냅니다. 모델을 바꾸지 않고도 틀린 크롭이 나오는 거예요.

그래서 에는 좌표 기준, 원본과 리사이즈 중 어느 크기인지, 카드가 없을 때의 응답까지 적어야 합니다.

모델 지표와 업무 결과도 따로 봐야 합니다. 사진 1,000장 중 재촬영 요청이 120장에서 70장으로 줄었어도, 잘못 잘라 낸 사진 40장을 다음 단계로 넘겼다면 재촬영 비율 하나로 성공이라 할 수 없어요.

헷갈리는 짝

원문이 "둘은 다르다"고 짚은 것들입니다.

학습 ↔ 추론

데이터와 정답으로 가중치를 구하는 과정. 공부.

학습한 모델에 새 입력을 넣어 예측. 시험.

핵심사진 한 장 요청이 올 때마다 모델을 다시 학습하지 않습니다.

평가 ↔ 사용 목적 검증

학습에 쓰지 않은 데이터로 성능을 잰다.

업무 요구를 만족하는지 확인하고 승인하거나 보류한다.

핵심조직마다 용어가 다르니 이름보다 절차와 책임을 합의합니다.

검증셋 ↔ 모델 검증

모델과 설정을 고르는 데 쓰는 데이터.

업무 관계자가 사용 목적에 맞는지 확인하는 절차.

핵심같은 단어라도 "누가 무엇을 확인하는가"를 붙여 읽어야 합니다.

실험 ↔ 운영

어떤 데이터와 모델이 효과적인가? 이번 결과가 좋은가?

다시 찾을 수 있는가? 실패를 감지하고 되돌릴 수 있는가? 다음 변경도 같은 기준으로 검증할 수 있는가?

핵심운영에서는 반복해서 안전하게 실행하고 바꾸는 능력이 중요해집니다.

재학습 ↔ 출시

새 후보를 만드는 과정.

그 후보를 사용자에게 연결하는 결정.

핵심점수가 좋아도 특정 문서 유형에서 실패하거나 응답이 느려졌다면 출시를 보류할 수 있습니다.

모델 파일 보관 ↔ 재현 가능한 상태

모델 파일 보관

가중치 파일이 어딘가에 있다.

그 파일을 만든 데이터, 분할, 전처리, 설정까지 다시 찾을 수 있다.

핵심가중치 파일만으로는 결과가 나쁜 이유를 알 수 없습니다.

파일 경로 ↔ 내용 해시

냉장고의 주소. 안의 내용은 바뀔 수 있다.

그때 들어 있던 내용의 지문.

핵심데이터 위치를 아는 것과 그때의 내용을 아는 것은 다릅니다.

release_id ↔ 모델 버전

서비스 출시 조합 전체의 이름.

레지스트리에 등록된 가중치 하나. 예: models:/card-detector/3

핵심서버 이미지는 그대로 두고 외부 모델 참조만 바꿔도 예측 결과가 달라집니다.

실험 추적 ↔ 모델 레지스트리

어떤 조건에서 어떤 결과가 나왔는지 기록.

그중 어떤 모델을 관리하고 서비스할지 등록.

핵심둘을 이어야 배포한 모델이 어느 실험에서 나왔는지 찾을 수 있습니다.

오케스트레이터 ↔ 학습 알고리즘

작업을 실행하고 순서대로 연결한다.

데이터에서 가중치를 찾는다.

핵심역할이 겹쳐 보이는 도구를 비교할 때 이 차이부터 봅니다.

자체 구축 ↔ 관리형 서비스

조정의 자유가 큰 대신 업그레이드, 장애, 사용자 지원을 감당.

구축 부담은 줄지만 통합, 권한, 비용 관리는 남음.

핵심오픈소스의 무료 사용과 무료 운영은 다릅니다.

MLOps ↔ LLMOps

MLOps

데이터, 코드, 설정, 가중치를 추적.

여기에 문서, 인덱스, 프롬프트, 모델 API, 답변 평가, 토큰 비용이 더해짐.

핵심어떤 문서와 프롬프트, 모델 API 조합으로 답했는지까지 추적해야 합니다.

객체 탐지 ↔ OCR

사진에서 카드가 어디 있는지 찾는다.

카드 안의 글자를 읽는다.

핵심책의 첫 프로젝트는 OCR 맥락 안에 있지만 학습 대상은 카드 위치 찾기입니다.

용어 사전

원문에 나오는 용어를 구역별로 모았습니다. 항목을 누르면 비유, 필요한 이유, 주의할 점이 펼쳐져요.

실습: 출시 조합 기록

    출시 하나를 이루는 조합을 JSON으로 적습니다.

    {
  "release_id": "card-study-001",
  "code_revision": "git-commit-of-training-code",
  "dataset_snapshot": "cards-synthetic-v1",
  "split_policy": "capture-session-grouped-v1",
  "preprocessing": "resize-and-coordinate-transform-v1",
  "model_uri": "models:/card-detector/3",
  "image_digest": "digest-of-serving-image",
  "evaluation_report": "reports/card-study-001.json",
  "rollback_release": "card-study-000"
}

  2. 상황별로 어디를 먼저 볼지 정하기

    어제와 같은 사진의 좌표가 달라짐

    먼저
    출시 → 모델, 전처리, 이미지
    이유
    가중치 외의 변경도 출력에 영향

    평가 점수를 다시 계산할 수 없음

    먼저
    실행 → 평가셋, 분할, 지표 정의
    이유
    점수만 저장하면 계산 조건을 잃음

    이전 모델로 돌렸는데 오류가 계속됨

    먼저
    이전 출시의 전처리와 API 규격
    이유
    모델만 되돌리면 호환되지 않는 조합이 남을 수 있음

  3. 해시로 출처가 바뀌는 순간 확인하기

    원문의 lineage_study.py와 같은 실험입니다. 파일 이름은 그대로 두고 내용에 한 줄을 더하면 지문이 어떻게 되는지 보세요.

    기록한 SHA-256 계산 중
    지금 SHA-256 계산 중
    Matches: True

    확인 처음엔 True, 한 줄 추가 뒤엔 False

  4. 결과 해석

    긴 해시 문자열을 외울 필요는 없습니다. 파일의 위치와 내용의 버전은 다르다는 것만 보면 돼요. 불일치가 나면 원본을 복구하거나 새 데이터 버전으로 실험해야지, 명세의 해시만 바꿔 맞추면 안 됩니다.

    주의 해시는 내용을 복구해 주지 않습니다. 원본 스냅샷도 보존해요. 같은 숫자까지 재현하려면 난수, 라이브러리, 하드웨어 영향을 따로 검증합니다.
