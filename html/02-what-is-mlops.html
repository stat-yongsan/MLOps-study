02장 용어를 공장으로 풀어 보기

02장은 예측 공장을 어떻게 운영할지 정하는 장입니다. 예측이 나빠졌을 때 바로 재학습하는 대신, 원인을 찾아 맞는 다음 행동으로 잇는 법과 자동화 수준을 다뤄요.

용어 이름을 누르면 설명으로 이동하고, 숫자로 보기에서는 값을 바꿔 직접 계산해 볼 수 있습니다.

MLOps 생애주기ML lifecycle생애주기

데이터 수집부터 모니터링, 개선까지 계속 도는 고리. 관측한 문제를 다음 행동으로 잇는 과정입니다.

비유
신제품 공장의 한 해. 재료 확보 → 재료 검수 → 시제품 개발 → 품질 시험 → 출시 → 판매 현장 관찰 → 개선 또는 단종, 그리고 다시 처음으로.
왜 필요해
모델은 한 번 만들고 끝나지 않습니다. 세상이 바뀌면 데이터와 정답의 관계도 바뀌어요.
엑셀로 치면
매달 갱신하는 보고서. 데이터를 받고, 이상한 값을 거르고, 수식을 고치고, 결과를 검토해 배포하고, 다음 달 피드백을 반영하죠.
주의
예측이 나빠졌다고 바로 재학습으로 가지 않습니다. 입력 스키마가 깨졌으면 수집으로, 평가 기준이 틀렸으면 문제 정의로, 서버가 느리면 서빙 구성으로 가요. 가치가 사라졌다면 폐기도 답입니다.
평가 지표precision · recall · MAE · MSE평가

모델이 얼마나 잘하는지 재는 자. 문제와 실패 비용에 맞는 자를 골라야 합니다.

비유
화재경보기. 오작동이 잦으면(precision 낮음) 사람들이 무시하고, 불을 놓치면(recall 낮음) 큰일이 납니다. 어느 쪽을 줄일지는 건물마다 달라요.
왜 필요해
"정확도 95%"만으로 배포를 정할 수 없습니다. 메일 1만 개 중 스팸이 100개라면 전부 통과시켜도 정확도 99%예요.
엑셀로 치면
행은 실제, 열은 예측인 피벗 테이블(혼동표)을 만들고 COUNTIFS로 비율을 구하는 것. 아래 "숫자로 보기"에서 직접 해 볼 수 있어요.
이번 장에서
스팸 예시에서 precision 약 66.7%, recall 80%.
주의
지표 이름보다 어떤 실패에 무게를 두는지가 중요합니다. 다중 클래스라면 macro, micro 같은 집계 방식까지 맞춰야 비교할 수 있어요.
드리프트P(X) · P(Y|X)모니터링

시간이 지나며 입력 데이터, 또는 입력과 정답의 관계가 바뀌는 것.

비유
데이터 드리프트는 가게에 오는 손님 구성이 바뀌는 것, 개념 드리프트는 같은 손님인데 사는 방식이 바뀌는 것.
왜 필요해
학습할 때의 세상과 지금의 세상이 다르면 모델이 틀리기 시작할 수 있습니다.
엑셀로 치면
지난달과 이번 달 피벗을 나란히 놓고, 연령대 비율이 바뀌었는지(데이터 드리프트), 같은 가격대만 필터했는데 구매율이 바뀌었는지(개념 드리프트) 보는 것.
주의
"드리프트가 났다"에서 끝내지 말고 무엇의 분포나 관계를 어떤 기간과 비교했는지 확인합니다. 변화가 있다고 반드시 품질이 떨어지는 것도 아니에요.
CI · CD · CT통합 · 배포 · 지속 학습자동화

CI는 코드 변경 검사, CD는 검증된 변경의 전달·배포, CT는 데이터 변화에 맞춰 학습을 다시 돌리는 것. ML에서는 CT가 더해집니다.

비유
CI는 생산 라인 설계 변경의 검사, CD는 바뀐 라인 설치, CT는 새 재료가 들어올 때마다 라인을 돌려 시제품을 다시 굽는 것.
왜 필요해
ML은 코드가 그대로여도 데이터가 바뀌면 모델을 다시 만들어야 합니다.
엑셀로 치면
CI·CD는 쿼리 수식을 고쳤을 때 검사 후 배포본에 반영하는 것, CT는 원본 데이터가 바뀌면 새로 고침해 보고서를 다시 만드는 것.
주의
CD는 delivery(출시 준비)와 deployment(자동 출시) 두 뜻으로 쓰입니다. 실행을 자동화해도 잘못된 데이터나 나쁜 후보의 출시는 막을 수 있어야 해요.
MLOps 성숙도Level 0 · 1 · 2성숙도

무엇을 반복 가능하게 만들었는지로 나눈 자동화 수준. 책은 Google의 구분을 소개합니다.

비유
Level 0은 수공업 공방, Level 1은 재료만 넣으면 돌아가는 생산 라인, Level 2는 생산 라인 개조까지 시험 가동 후 자동 반영되는 공장.
왜 필요해
다음에 무엇을 자동화할지 고르는 기준이 됩니다.
엑셀로 치면
Level 0은 매달 복사·붙여넣기로 만드는 보고서, Level 1은 파워 쿼리 새로 고침 한 번으로 검사·가공·보고서까지, Level 2는 쿼리 단계를 고칠 때도 테스트를 거쳐 배포본이 자동 갱신되는 것.
주의
높은 수준이 무조건 목표는 아닙니다. 성숙도는 재학습 빈도가 아니라 잘못된 입력과 변경을 거절하고 원인에 맞게 복구하는 능력으로 봐요.
검증 게이트release gate성숙도

잘못된 입력이나 기준 미달 후보가 다음 단계로 넘어가지 못하게 막는 검사 지점.

비유
컨베이어 벨트 끝의 불량품 검사대. 검사대 없는 벨트는 빠를수록 위험합니다.
왜 필요해
자동화가 빨라질수록 나쁜 모델도 빨리 나갑니다. 멈추는 장치가 있어야 자동화를 믿을 수 있어요.
엑셀로 치면
데이터 유효성 검사에 IF 조건을 더해, 기준 미달이면 "보류"와 이유를 띄우는 검사표.
이번 장에서
스키마 일치, 결측률 1% 이하, 기준선 대비 검증 AUC +0.02 이상, p95 지연 200ms 이하를 모두 만족해야 통과(eligible)입니다.
주의
AUC가 0.99여도 결측률이 8%면 통과하지 못합니다. eligible은 출시 완료가 아니라 "적힌 검사는 통과했다"는 뜻이에요.

숫자로 보기

원문의 스팸 예시와 실습 코드를 그대로 옮겨 왔습니다. 값을 바꾸면 결과가 바로 바뀌어요.

정확도 99%의 함정

실제 \ 예측스팸으로 차단정상으로 통과
스팸 100개8020 FN
정상 9,900개40 FP9,860
정확도99.4%
precision66.7%
recall80%

차단한 120개 중 80개가 스팸이라 precision은 80 ÷ 120, 스팸 100개 중 80개를 잡아 recall은 80 ÷ 100입니다. 반대로 전부 정상으로 통과시켜도 정확도는 99%지만 recall은 0%예요.

통과

원문 코드는 결측률을 0.005처럼 비율로 받습니다. 0.08은 8%이지 0.08%가 아니에요. 여기서는 헷갈리지 않게 % 단위로 입력합니다.

헷갈리는 짝

원문이 "둘은 다르다"고 짚은 것들입니다.

데이터 드리프트 ↔ 개념 드리프트

입력 분포 P(X)의 변화. 손님 구성이 바뀜.

입력과 정답의 관계 P(Y|X)의 변화. 같은 손님이 사는 방식이 바뀜.

핵심둘은 함께 생길 수도 있고, 변화가 있어도 품질이 그대로일 수도 있습니다.

Precision ↔ Recall

차단한 것 중 진짜 스팸의 비율. 정상 메일을 잃는 비용이 클 때.

진짜 스팸 중 잡아낸 비율. 스팸을 놓치는 비용이 클 때.

핵심어느 쪽을 택할지는 업무의 손실 구조가 정합니다.

MAE ↔ MSE

오차 절댓값의 평균. 모든 오차를 같은 무게로.

오차 제곱의 평균. 큰 오차를 훨씬 무겁게.

핵심큰 실수 한 번이 치명적인 문제라면 MSE 쪽이 맞습니다.

정확도 ↔ 실패 비용

맞힌 비율. 모든 실수를 같은 무게로 센다.

FP와 FN에 각각 업무상 손실을 매겨 합한다.

핵심두 실수를 같은 비용으로 치면 업무에 맞지 않는 모델을 고를 수 있습니다.

ROC-AUC ↔ 임계값의 손실

점수로 줄 세우는 능력의 요약.

실제로 쓸 기준선. FP와 FN 개수는 여기서 정해진다.

핵심AUC가 높다고 실제 손실까지 최소인 것은 아닙니다.

검증셋 ↔ 테스트셋

후보와 임계값을 고르는 데 쓰는 모의고사.

마지막 확인에만 쓰는 수능.

핵심테스트 결과를 보며 계속 고르면 그 데이터도 선택에 쓰인 셈입니다.

스키마가 맞음 ↔ 데이터가 유효함

rating 열이 숫자다. 셀 서식이 맞다.

그 숫자가 허용 범위 안에 있다. 유효성 검사를 통과한다.

핵심타입, 값의 범위, 다른 열과의 관계를 함께 봐야 합니다.

하이퍼파라미터 ↔ 가중치

학습률, 모델 크기처럼 사람이 정하는 조건.

가중치

학습이 데이터를 보며 스스로 찾아내는 값.

핵심엑셀 해 찾기로 치면 제약·옵션은 사람이, 변수 값은 해 찾기가 정합니다.

대리 신호 ↔ 정답 기반 품질

입력 분포, 결측률, confidence. 바로 볼 수 있다.

실제 정답이 도착한 뒤에야 계산된다.

핵심confidence나 드리프트는 조사 신호이지 정확도의 증명이 아닙니다.

CI·CD ↔ CT

파이프라인 코드가 바뀔 때. 검사, 빌드, 배포.

데이터나 일정이 바뀔 때. 검증, 학습, 평가 실행.

핵심코드 변경 경로와 데이터 변경 경로는 따로 돕니다.

delivery ↔ deployment

언제든 출시할 수 있는 상태까지 준비.

운영에 자동으로 출시.

핵심둘 다 CD라고 부르므로 승인 경계를 분명히 적어야 합니다.

Level 1 ↔ Level 2

정해진 학습 절차를 자동으로 다시 돌린다.

학습 절차 자체를 고칠 때도 검사, 빌드, 배포가 자동.

핵심모델이 자주 나오는 것과 모델을 만드는 시스템을 안전하게 바꾸는 것은 다른 능력입니다.

DevOps ↔ MLOps

코드, 설정, 의존성 변경을 다룬다. 오류율과 지연을 본다.

데이터와 모델 변경까지 다룬다. 입력 분포와 예측 품질도 본다.

핵심절대적 경계가 아니라 ML에서 더 분명히 추적할 것이 무엇인지 보는 비교입니다.

용어 사전

원문에 나오는 용어를 구역별로 모았습니다. 항목을 누르면 비유, 필요한 이유, 주의할 점이 펼쳐져요.

실습 순서와 등장 용어

모델을 학습하는 코드가 아니라, 평가 결과를 받아 후보를 거르는 규칙을 연습하는 실습입니다.

  1. 실패 비용 계산

    error_cost() 함수로 FP 100, FN 2를 가정해 두 모델의 손실을 비교합니다. cost_study.py로 저장해 실행해요.

  2. 출시 게이트 만들기

    release_decision()이 결측률, 검증 AUC, 기준선 AUC, p95 지연, 스키마 일치를 받아 통과 여부와 이유를 돌려줍니다. 빠진 항목이나 NaN 같은 값은 오류로 거절해요.
