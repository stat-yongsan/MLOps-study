도구 이름보다 역할로 기억하기

책에 도구가 아주 많이 나옵니다. 공장의 어느 자리인지로 묶어 두면 새 도구가 나와도 "이건 그 자리의 다른 선택지"로 읽을 수 있어요. 도구 이름을 누르면 설명으로 갑니다.

헷갈리는 짝

책을 읽기 전에 미리 구분해 두면 좋은 것들입니다.

API로 배포하기 ↔ 다시 만들고 안전하게 바꾸기

API로 배포

모델을 한 번 서비스에 올린다.

플랫폼의 일

그 모델을 다시 만들고, 검증하고, 바꾸고, 되돌릴 수 있게 한다.

핵심이 책은 학습 코드보다 데이터, 실험 기록, 배포, 복구를 잇는 쪽을 다룹니다.

도구 설치 ↔ 플랫폼 완성

도구 설치

MLflow, Feast, KFP가 떠 있다.

운영 책임, 장애 대응, 인수 자료까지 갖춰져 있다.

핵심도구가 있어도 운영 책임과 장애 대응이 빠지면 완성이라 보기 어렵습니다.

모델 크기 ↔ 검색 품질

답을 더 잘 쓸 수는 있다.

애초에 맞는 문서를 찾아야 한다.

핵심문서를 잘못 찾으면 모델이 커져도 답이 좋아지지 않을 수 있습니다.

검색 붙이기 ↔ 위험 해결

근거 문서를 참고해 답한다.

권한, 근거 확인, 입출력 검사가 따로 필요하다.

핵심검색을 붙였다고 환각이나 정보 유출 위험이 사라지지는 않습니다.

가중치 관리 ↔ LLM 운영

Part 1~3

직접 학습한 모델의 가중치, 데이터, 코드를 관리.

검색 문서, 벡터 인덱스, 프롬프트, 외부 모델 API 관리가 더해짐.

핵심추적할 대상이 늘어날 뿐, 출처·근거·복구라는 질문은 같습니다.

책의 동작 원리 ↔ 최신 버전에서 실행

동작 원리

왜 이렇게 연결하는지는 버전과 상관없이 유효.

명령과 API

KFP의 데이터 전달, BentoML의 Service·Runner API, MLflow 모델 단계 관리는 지금과 다를 수 있음.

핵심04장 실습에서 MLflow stage 경고가 뜬 것도 이 차이 때문입니다.

설계한 구조 ↔ 실제 구현

설계

그림과 문서에 적힌 구조.

구현

실제로 돌려 본 결과. 성능과 복구 시간은 여기서 확인.

핵심성능과 복구 시간은 실행 결과로 확인해야 합니다.

도구 사전

책에 나오는 도구와 개념을 역할별로 모았습니다. 03·04장에서 자세히 다룬 도구는 해당 페이지로 이어져요.

실제 업무와 연결하기

구간마다 엔지니어가 결과물로 남길 것입니다. 읽으면서 "우리 일에서는 이게 뭘까"를 같이 떠올려 보면 좋아요.

1~3장생애주기, 책임 경계, 재현 가능한 실행, 배포 기반
4~6장실험, 피처 계보, 작업 계약, 서비스와 드리프트 대응
7~9장 검증 게이트, 학습 자원, 성능 측정
10~11장출시 명세, 부하, 복구 결과, 와
12~13장검색, 답변 평가, 권한 경계, 변경, 비용 통제

프로젝트에서 확인할 것

  1. 문제와 기준: 업무 목표, 데이터 사용 범위, 현재 병목과 성공 기준.
  2. 설계 결정: 채택하고 제외한 대안, 의존성, 운영 비용과 담당자.
  3. 검증 증거: 데이터, 모델, 서비스 시험 결과, 실패 재현과 복구 기록.
  4. 인수 자료: 배포와 롤백 절차, SLO, 알림, 실행 지침, 접근, 보존 정책.
책의 도구를 모두 설치하는 것보다, 지금 반복해서 겪는 실패가 무엇이고 그 판단 근거를 어디에 남길지 정하는 편이 먼저입니다. 정확도가 높은 모델을 고르는 일도 지연 시간, 데이터 누수, 재현성, 복구까지 함께 보면 다른 결정이 될 수 있어요.
